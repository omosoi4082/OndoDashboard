## 10/29 확인 요청에 대한 답

1. **중계 서버 창**: 어제 창은 닫아서 로그가 남아 있지 않다.
2. **연산 서버**: 재시작 없었다. 다만 10/29에는 **연산 서버 PC와 중계 서버 노트북 모두에서 다른 계산 작업이 돌고 있었다.**
   10/30은 노트북은 비어 있고 연산 서버 PC에서만 모델 학습이 돈다(이번 주말까지). 그래서 예측 1건이 평소보다 오래
   걸려 **10/30 trace에서도 예측 요청이 12.5초**였다.
3. **viz**: 응답이 **6.4 MB → 15.7 MB**(gzip 1.0 → 2.1 MB), 처리 시간 약 2배. 응답 크기 제한은 없다.
   다만 **연산 서버는 한 번에 1건만 계산하고, 계산 중에 들어온 요청은 바로 503 BUSY로 돌려보낸다**(10/13 D-4).
4. **네트워크**: 중계 서버 노트북과 연산 서버 PC(192.168.10.91)는 같은 사무실 Wi-Fi(AP: Ruckus R650).
   그 시간 Wi-Fi 끊김이나 AP 재시작은 없었다.

온도 측 추정: 두 PC가 모두 바쁜 상태에서 예측 처리가 길어져, **요청이 겹친 순간에 BUSY를 받은 것**(확정은 아니라고 밝혔다).

## 우리 쪽 결론 (2026-10-30)

3번 답("한 번에 1건, 계산 중 요청은 BUSY")으로 **10/29 실패 7건의 원인이 우리 쪽으로 특정됐다.**

- `useCurrentDetailPolling`이 App 마운트에 걸려 있어 **접속 즉시 `/api/detail/current`**(연산 1건)를 보낸다
  (`usePolling`은 즉시 1회 + 10분 주기).
- B-3 테스트는 `beforeEach`마다 `page.goto('/')`를 하고 곧바로 예측 탭을 누르므로,
  **`/api/detail/forecast`가 현재 모드 연산이 끝나기 전에 들어간다**. viz 켜진 1건이 12~25초라 겹침이 자주 생긴다.
- 겹침은 경합이라 **같은 시간대에 성공과 실패가 섞이고**, 페이지·glb 로드가 빨랐거나 현재 모드 연산이 먼저 끝난
  회차는 통과한다 — 노트북이 비어 있던 10/30에 재현되지 않은 것도 이것으로 설명된다.
- 실패가 BUSY 문구가 아니라 `UPSTREAM_UNREACHABLE`(fetch 예외, 9~19초)로 온 점은 연산 서버가 이 경로에서
  503 대신 연결을 끊는 것으로 보이지만 **확정은 아니다**. 어느 쪽이든 겹침을 없애면 생기지 않는다.
  (BUSY 응답이었다면 그때 코드는 1분을 기다렸다 재시도하므로 9~19초가 아니라 60초 이상 걸렸을 것이다.)

→ 요청 1번을 그대로 반영했다(`clients/computeQueue.ts`, `clients/computeRetry.ts`, `docs/03` 4.2, `docs/05` #45).
10/29 문서의 (다)안(연결 실패 시 1회 재시도)은 **넣지 않는다** — 원인이 우리 쪽 겹침이라 실패를 가리는 대신 겹침을 없앴다.
